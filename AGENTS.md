# HoloRecall working agreement

- Treat [the product charter](docs/HoloRecall_Product_Charter_v1.md) as the authoritative direction and delivery contract. Will is product director, ChatGPT defines milestones, and the lead Codex agent owns engineering coordination, integration and evidence. Proposed commercial choices remain proposals until Will approves them.
- Use [product brief and capability roadmap](docs/product-brief.md), [work-item tracker](docs/work-items.md), [architecture and design rules](docs/architecture.md), [cross-platform evidence](docs/ios-readiness.md), [deck format](docs/deck-format.md), [Anki compatibility](docs/anki-import.md), and [current restart handoff](docs/project-status.md) as the maintained sources of truth.
- Work autonomously through the currently authorized milestone, including Material 3 themes, Design Studio, illustrations, cosmetics, exchange and reports. The user's latest authority supersedes the original one-operation pause cadence. Give brief progress updates and continue through implementation, tests, fixes and starting the server.
- Pause only for a genuine blocker, destructive action, unavailable credentials, paid resources or external publishing. Do not deploy or push without authorization.
- Keep project writes inside this repository. Preserve existing work; never fabricate Git identity, force-push, reset study data silently or change global machine settings.
- Use pinned, supported dependencies and the lockfile. Check official documentation and installed APIs for version-sensitive decisions. Record material architecture changes before implementing them.
- Keep domain scheduling independent of Angular and visual effects. Ratings 1/2/3/4/5 map to FSRS Again/Hard/Good/Good/Easy; preserve the original rating. Inject time and disable scheduling fuzz in deterministic tests.
- Separate card content from learner state. Save reviews atomically with state, unique event IDs and concurrency versions. Preserve immutable review events; undo appends a reversal. Never represent sample gallery states as earned progress.
- Use original bundled assets, accessible reveal controls, readable effects and reduced-motion support. Keep unrevealed answers out of the accessible UI.
- Use Angular Material's public M3 theming APIs and shared system tokens for custom components; never style private Material internals. Theme defaults to System, with an early startup preference to prevent a light flash.
- Apply the layout review gate to changed flows: shared spacing and column tracks; start-aligned prose; useful numeric alignment; deliberate focal centring only; complete themes; accessible contextual help; stable Study geometry; restrained motion; minimal copy. WCAG 2.2 AA is a target, not a conformance claim.
- Designs are declarative raster assets and validated settings. Separate content rarity, earned cosmetics and scheduling difficulty. Reward contributions must be scheduled, spaced across study days, auditable, idempotent and reversible on undo.
- Preserve the existing IndexedDB database and migrate atomically with a retained legacy snapshot. Content imports must preview changes and preserve scheduling/review history; full progress backup is a separate format.
- Browser storage is local prototype storage, not cloud sync or guaranteed durable backup. Keep credentials, .env files and personal study exports out of Git.
- Keep documentation lean: README.md, docs/product-brief.md, docs/architecture.md, docs/project-status.md, docs/deck-format.md and the reusable deck-generation prompt. Product scope belongs in the brief; implementation evidence and one next action belong in status. Do not duplicate these rules elsewhere.
- Run focused domain and browser checks appropriate to the change. Report only tests actually run, and distinguish browser emulation from native device verification.
- For each meaningful change, proportionally assess learning integrity, UI consistency, web/iOS/macOS behavior, portability and entitlement impact. Product access, authored rarity, finishes, earned cosmetics and learning progress remain separate.
- Treat Web and future Capacitor iOS behavior as a standing concern for every meaningful change. Proportionally assess WebKit, touch/safe areas/keyboard/accessibility, persistence and interruption, animation cleanup, browser APIs needing native implementations, and actual verification. Maintain the evidence matrix and native-only gaps in `docs/ios-readiness.md`; never call Chromium, Playwright WebKit, a viewport preset or a mock “iOS verified.”
- New page sections should use the shared `hrReveal` block entrance unless accessibility, interaction or performance calls for an explicit exception. Animate meaningful wrappers rather than individual controls; keep Study's active deck/controls and component-owned transitions out of generic page motion.
- Layout and reward-motion changes require animation-enabled Chromium and WebKit evidence that samples alignment and intermediate timing, not only final screenshots or element presence. Content importers must maintain a documented compatibility matrix covering tested source variants, unsupported features, limits and fixture provenance.
- For every request, identify each distinct bug, change or feature in `docs/work-items.md` before implementation. Reuse an existing stable ID; otherwise assign one. Move started work to `IN_PROGRESS`, implemented work to `VERIFY`, and only evidence-backed work to `DONE`. Use `BLOCKED` when required clarification or an external dependency prevents progress. Never silently omit or delete an item, and keep unfinished work visible across runs. After each coherent implementation-and-test batch, update `docs/project-status.md` with the exact restart point.
- The repository tracker is the canonical execution record. GitHub Issues may later mirror collaboration or release work, but must not become a second independent source of truth.
